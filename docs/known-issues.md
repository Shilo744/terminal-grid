`Collected by the worker during the V4 run (newest at the bottom). `MORNING.md` is built from this list.

`## Fixed in V4, but the live V3 app has the same bug
`- **Silent save failure on Windows (state.json, and now settings.json).** `fs.renameSync(tmp, file)` throws `EPERM` when another process
`  (antivirus, the search indexer, an editor, a test polling the file) has the target open at that moment. V3 swallowed the error, so a terminal
`  list or a setting was simply not saved until the next change. V4 writes through `server/atomic-write.js` (retry with short waits, then a direct write).
`  It was found because the settings-panel test failed about once in four runs. If V3 keeps running next to V4, its `state.json` can still lose a save.
`
`## Test and tooling notes
`- **The machine is shared and often at 50-100 percent CPU** (other Chrome windows, OneDrive, a game launcher). Timing-based tests are the first to suffer;
`  the suite polls real conditions instead of sleeping, retries a failed file once and prints `FLAKE:` when that happens. The agent-pair UI test
`  (`e2e/duo-ui.js`) is the slowest and the most load-sensitive: the product itself waits 20 s for an agent to acknowledge an injected instruction and then backs off 60 s,
`  so a starved machine can push the whole loop past a test budget.
`- **Headless-Chrome screenshots can come out half empty under load** (missing stage, or terminals without text because the first WebGL paint did not happen yet).
`  Always look at the PNG; re-render that scene. `--disable-gpu` makes it worse for the screenshot tool, so it is not used there.
`- `tests/.tmp` collects Chrome profiles when a test is killed in the middle; `npm test` cleans them at the start.
`- **On a saturated machine (whole-machine CPU above ~90 percent, background load before the run 85 percent+) a few timing tests fail even on retry**: `e2e/latency.js` (p95 echo latency, server loop blocks of 1.5 s are the OS not scheduling the test server), `e2e/rtl.js` ("clearing the selection brings it back"), `server/history.js` (a 1.2 s scan takes 15-20 s). Each of them passes when run alone. They are not code regressions (seen in the T27 and T11 full runs at 98 percent CPU); the history test compares against the scan time instead of absolute milliseconds for that reason.
`- Found by a flaky test, not by eye: **hiding a terminal (tile, parked pair pane) used to make it jump to the top of its scrollback when shown again** (xterm resets its scroll area while the host is `display:none`). Fixed in `renderer-pool.js` (position remembered and restored, with a 3 s guard against the late jump); covered by `tests/unit/renderer-pool.js` and `tests/e2e/tiles.js`.

`## Tiles and parked panes (T27)
`- **A tile keeps the terminal size it had.** Tiles used to be re-fitted (and their PTY resized) on every window resize; now their host is hidden, so nothing is measured until the tile is expanded, then it is fitted once and the PTY is resized once (Claude redraws its screen). Visible effect: expanding a tile after the window was resized can show one redraw.
`- **The tile preview is a heuristic.** It shows the last two lines of the xterm buffer that contain a letter or digit, after trimming box-drawing characters at the line ends and skipping Claude's "? for shortcuts" / "(shift+tab to cycle)" hint lines. A different Claude Code version that words these hints differently will show them in the tile until the filter is adjusted (`HINT` in `public/js/tile-preview.js`). Hebrew lines are shown cell by cell left to right (as Claude sends them, already in visual order), not through the RTL layer.
`- Tiles can still only be activated with the mouse (click anywhere on the tile, or Alt+1-9); they are not keyboard-focusable. This was already so in V3; T9/T19 are the place to fix it.
`- WebGL cap: at most 8 panes hold a context. With more than 8 terminals visible in the grid the extra ones use the DOM renderer (correct, slower; box-drawing characters can show hairline gaps there). Focusing such a pane gives it a context and takes one from the least recently focused pane.
`- `/api/history` can answer `partial: true` (with the previous result) when the very first scan of a huge history takes more than 1.5 s; the sidebar asks again after 2.2 s. The agent-pair path still calls the synchronous `transcriptExists` once per agent start (one `existsSync` per project folder, cached); only the restore-on-start path is async.

`## Agent status from Claude hooks (T11) — to verify once on a real Claude terminal
`- Every plain Claude terminal now starts as `claude --settings "<tmp>/tg-agents/<conversation-id>.settings.json" --session-id|--resume <id>`; the file defines four hooks (SessionStart, UserPromptSubmit, Stop, Notification) that run
`  `node ".../server/duo/hook-cli.js" start|submit|stop|notify` (T28: the bare-`node` form, the same as agent pairs, see below) and post to `POST /api/agent/event`. The suite proves the command line, the file, the environment (`TG_PANE_ID`, `TG_PORT`), the endpoint, hook-cli itself and the UI mapping with a fake `claude`;
`  it cannot prove that the real Claude Code runs those hooks. If the pane header never leaves the old output-timing behaviour (`data-agent` attribute missing on `.pane`), the hooks did not fire: check `claude --settings` support in the installed version and that `node` is on the PATH of the Claude terminal (`server.log` has a `WARNING: node is not on the PATH` line at server start when it is not).
`- Handled hook/notification types: `SessionStart` (all sources; a mid-turn `compact` keeps "working"), `UserPromptSubmit`, `Stop`, `Notification` with `notification_type` `permission_prompt` or `elicitation_dialog` (or a message that contains "permission"). Other notification types (`idle_prompt`, `auth_success`, ...) are ignored on purpose.
`- **"Needs your attention" is cleared by typing in the pane, not by a hook.** Claude sends no hook when a permission is granted, so after "permission needed" the state stays `attention` until `Stop`; the UI treats the first key typed in the pane after the notification as the answer and shows "working" again. A `PostToolUse` hook would make this exact but fires after every tool call (one process start each), so it is not enabled.
`- A terminal whose hooks file could not be written (temp folder not writable, or a path containing `"`, `$` or a backtick) opens without `--settings` and keeps the old heuristic; the reason is in `server.log` (`agent hooks settings failed`).
`- Terminal Grid's own variables (`TG_PANE_ID`, `TG_DUO_ID`, `TG_DUO_ROLE`, `TG_PORT`) are now removed from the environment passed to every terminal (`cleanEnv`) and added back only where they belong. Found because the test servers inherited the duo variables of the agent session that ran them.
`- The settings file is per conversation id and stays in the temp folder (tiny, overwritten on every start); nothing deletes it.

`## Hook command shell-proofing (T28) — verified by hand on 2026-10-16
`- The hook command is `node "<hook-cli path, forward slashes>" <event>`. A command that starts with a quoted program path (`"C:/Program Files/nodejs/node.exe" "..." start`) is a **parse error in PowerShell**, so the first T11 form would have failed silently if Claude Code ran hooks through PowerShell; no quoting of a program path works in bash, cmd and PowerShell alike, so the bare `node` is used and the server checks once at start that `node` resolves on the PATH its terminals inherit (`where node`; a clear `WARNING: node is not on the PATH ...` goes to `server.log`; agent pairs have the same limit).
`- Observed, with a throw-away local HTTP listener on a free port and the real `hook-cli.js` (not from a test script, from the worker's own shells): **bash** `bash -c 'node "<cli>" start'` with JSON piped in and with `< /dev/null` -> the POST to `/api/agent/event` arrived both times and exit code 0; **PowerShell 5.1** `node "<cli>" notify` (with `$env:TG_PORT` / `$env:TG_PANE_ID` set) -> POST arrived, exit 0; the absolute-path form in PowerShell -> `Invoke-Expression` fails with a parser error (confirmed, not delivered). **cmd.exe** was not run by hand (a quoted path argument to a bare `node` is plain cmd syntax).
`- Found on the way: PowerShell's pipeline prepends a UTF-8 BOM to text piped to a native program; `hook-cli.js` used to fail `JSON.parse` on it silently (the event arrived with no fields). It now strips a leading BOM (unit-tested).
`- The agent environment of this very run has `TG_DUO_ID`/`TG_DUO_ROLE` set (the worker is itself an agent pair member), which is why a manual `hook-cli` run from that shell takes the duo route unless those variables are removed first (`env -u TG_DUO_ID -u TG_DUO_ROLE ...`).

`## Pane menu and restart (T9)
`- **Restart** (menu item or the overlay button) is only offered for a terminal whose process exited; it opens a new terminal in the old one's place (order, expanded and focus move to it) and closes the old one. `## Autostart and pairs after a restart (T30)
`- The switch creates a shortcut in the user's Startup folder; Windows runs it **after sign-in**. Without Windows auto sign-in nothing starts after a reboot until someone signs in (README explains netplwiz / Autologon and the security trade-off).
`- Verified by hand (not by a test script): a real `.lnk` created in a TEMP folder through the server (target `conhost.exe`, arguments `--headless powershell.exe -NoProfile -ExecutionPolicy Bypass -File "<root>\start.ps1" -NoBrowser [-Port n]`, working directory = project root, app icon, read back with WScript.Shell) and the exact command line started headless on port 7797 (the server came up with `.state-7797`; that exact PID was stopped). **Not verified:** a real Windows reboot with the shortcut in the real Startup folder.
`- `system.autostart` is a virtual setting: it is never written to settings.json and `settings:set` cannot change it; only `POST /api/autostart` (origin-checked) creates or removes the file. Tests use `TG_TEST_STARTUP_DIR` (a temp folder) and `TG_TEST_AUTOSTART_STUB=1` (a JSON file instead of PowerShell); nothing in the real Startup folder was ever touched.
`- A pair that was working at the last save is woken again after a restart; the "last save" is written at every start/end of a turn, so a power cut loses at most the turn in progress (which is exactly what is resumed). A worker is continued only if its task file still has open tasks.
`- The shortcut name depends on the port, so running the same project on two ports needs two switches (one per instance).

`## V4 window opens in its own Chrome profile (T31)
`- **Finding (architect, 11:3x on 2026-10-16):** a frozen copy of V4 on port 7796 opened with `chrome.exe --app=http://127.0.0.1:7796/` in the user's normal Chrome produced **two blank grey windows** (title `127.0.0.1_/`, the server saw an open socket but no WebSocket client). The same URL rendered correctly in clean headless Chrome and in a real window of a separate Chrome with a fresh `--user-data-dir` (title "Terminal Grid", one client). So the server and the page are fine; something in the everyday Chrome profile (an extension, a setting, or Chrome state) hangs a brand-new local origin. **The cause in the main profile is unknown** (not investigated further; the live instance on 7791 is an old origin the profile is happy with).
`- **Change:** for any non-default port `start.ps1` starts Chrome (or Edge) with `--user-data-dir="<root>\.chrome-<port>" --no-first-run --no-default-browser-check --window-size=1500,950 --app=<url>`: its own browser instance, the user's browser process is never reused or touched. The default port 7791 keeps the old behaviour exactly. "Window already open" is decided per port: if the instance has a client, the window of THAT dedicated profile (found through its command line) is raised, never the window of the instance on 7791. `.chrome-*` is git-ignored.
`- A first start in a fresh profile may show Chrome's own first-run UI for a second (`--no-first-run` suppresses most of it); the profile is a few tens of MB after a while and can be deleted any time (it only holds Chrome's own state for that window).

`## One state for a pair agent (T43)
`- The pair server state of an agent (`starting | idle | working | attention | exited`, from the pair hooks) is also stored on the session (`agentState/agentSince/agentSource = 'hooks'`) and broadcast as the same `agent` message regular Claude terminals use (`server/duo/manager.js` `syncAgentPanes`, debounced 150 ms with the duo state). So the pane header of a pair agent (T12 pills: "עובד…", "צריך אישור"), the agent card on the board (state dot + word + accent tint when working), the tab dot and the top summary always agree (`tests/e2e/duo-state.js` drives real hook events and asserts all of them). A pair agent that finished its turn is "idle" (no "waiting for you" pill: nobody has to read it), unlike a regular Claude terminal.
`- The task list groups by state (בעבודה, הבאות (first 5, "ועוד N בהמשך"), חסומות, הושלמו (N) collapsed, remembered per pair in localStorage `tg.duoDone-<id>`), with sticky group headers and 2-line titles (full title in the tooltip); the current task is scrolled into view the first time and whenever a task changes state. Compare scene: `node tests/tools/scenes.js duo-board-many` (41 tasks).

`## Pair tab dot, alerts and tab order (T46)
`- The dot of a pair is ONE current state (`duoStatus`, fed by the single pair state of T43 plus the UNRESOLVED alerts): working = accent with a slow pulsing ring, idle = grey, paused = grey with a pause glyph, needs you now = amber (an agent waits for approval, or an alert that is still true), problem = red (an agent closed). Tooltip on the dot and on the tab/side-menu row: one Hebrew line from `duoReason` ("עובד עכשיו: העובד מבצע T7", "מחכה לך: הארכיטקט ממתין לאישור הרשאה", "הכול תקין, ממתין למשימה הבאה", "מושהה", "בעיה: העובד נסגר"); a "?" in the tab row opens the legend.
`- Alerts have a `key` and clear themselves (`server/duo/duo.js` `alert/resolve`): `permission:<role>` when the agent submits, stops or starts again; `closed:<role>`, `nostart:<role>` and `notreceived:<role>` on the next hook event of that agent; `stuck` when the worker makes progress or the tasks change. The snapshot carries only unresolved alerts; the history stays in "פעילות אחרונה" ("התראה: ..." and "נפתר: ..."). An agent that exits does NOT come back by itself (nothing restarts a pair agent), so "closed" stays red until the pair is recreated: that is a real problem, not a stale warning.
`- Tabs are draggable with pointer events (lifted tab, the others slide; a click without movement still selects) and Alt+Shift+Left/Right moves the focused tab (announced through an aria-live region). The order is the order of the server's `duos` map: the `duo` op `reorder` (ids validated, unknown ignored, unmentioned kept at the end) re-orders it, persists it to state.json and broadcasts `{op:'order'}`; the tab row, the side-menu list and a restart all use it. "+ זוג חדש" is always last and not draggable.

`## Links in terminals (T47)
`- xterm.js makes OSC 8 hyperlinks (and, with the WebLinks addon, plain http/https text) clickable. Terminal Grid sets its own handlers (`public/js/links.js`): only Ctrl+click activates; http/https open with `window.open(uri, "_blank", "noopener,noreferrer")`; any other scheme is copied to the clipboard with a toast and never navigated; a hover chip names the target; a document-level capture handler cancels clicks on non-web anchors (none exist today). `allowNonHttpProtocols: true` is set on purpose: without it xterm ignores mailto:/file: links completely (no chip, no copy). **The source of the Windows "choose an app for this mailto link" dialog the user saw was not proven**: nothing in our code creates a mailto link and the xterm 6 default skips non-http OSC 8 links, so the most probable source is outside the terminal (for example a link inside the page opened by the browser itself); if the dialog appears again, note what was clicked.

`## Auto-accept of the folder trust prompt (T32) — verify once with a real Claude
`- The server reads the visible screen of every NEW Claude terminal (including pair agents) for the prompt (`trust this folder` together with `Enter to confirm`, or the old wording `Do you trust the files in this folder`). **The real dialog highlights "No, exit" first** (the first version, T32, assumed "Yes" and pressed Enter on "No": Claude quit; fixed in T40): `server/trust.js` `trustChoice(text)` finds the single marked line (`❯`, `›` or `>`, with or without "1. ") and answers `enter` only when it is "Yes, I trust this folder", `down` when it is "No" with the Yes option below it, and nothing otherwise (no marker, two markers, unknown line). `watchTrust` waits 150 ms and reads the screen again, sends Down (`ESC [ B`), waits until the marked line actually changes (never a second Down blind; gives up after 1.5 s or 5 steps) and only then Enter. Window: 45 s from the spawn (test hook `TG_TRUST_WINDOW_MS`), once per terminal. PowerShell terminals and every other dialog (e.g. the "bypass permissions" acceptance) are never answered; `~/.claude.json` is never touched.
`- **By the user's decision there is no setting, no warning and no toast** (opening an agent in a folder already is the decision to trust it); the only switch is the environment variable `TG_AUTOTRUST=0` on the server, used by the tests. Each accept is logged in `server.log` (`auto-trust accepted <id> <folder>`). For agent pairs the "did not start, maybe approve trust" alert is not raised when the accept happened (tested with a positive control: with `TG_AUTOTRUST=0` the same pair does raise it).
`- **Detection depends on the English wording of the prompt.** If Claude Code changes it, auto-accept silently stops working and the manual click comes back (no harm). Not verified against a real Claude Code (fake `claude` only: `tests/fixtures/trust.js` reproduces the real layout from the user's screenshot, `tests/fixtures/trust-real-prompt.txt` is that text, and `tests/unit/trust-choice.js` + `tests/server/trust.js` assert one Down then one Enter, never Enter on "No"): it is item 4 in the "verify once with a real Claude" list in MORNING.md.

`## Paste speed (T33)
`- A paste is handed to the program by Windows ConPTY at roughly **15-20 KB per second here** (20 KB in about 1 s, 200 KB in about 14 s); this is the whole delay, measured stage by stage in docs/performance.md. The browser and the server add under 1 ms; chunking the writes does not help (tested). Terminal Grid cannot make ConPTY faster; the real Claude Code may read input faster or slower than the fake program used for the measurement (not verified with a real one).
`- During a big paste the UI and the other terminals stay responsive (tested: worst server ping 14 ms, a keystroke in another terminal echoed after 0.75 s), but the pasted terminal itself receives the rest of the text only as ConPTY delivers it.
`- The stage "echo visible in the xterm buffer" was not measured on this saturated machine (see the performance notes).
`
`## Restarting a pair agent (T51)
`- A pair agent counts as **exited** when its terminal process ends or the terminal is closed: its card turns red with a "הפעלה מחדש" button (and the terminal shows "התהליך הסתיים" with the same button). Restart runs `claude --resume <same conversation>` (`--session-id` when no transcript exists yet) with the same role, hooks and settings; an exited worker with open tasks is woken with the "continue" text, an architect that closed in the middle of a turn is woken once.
`- **Not detected: Claude quitting while its PowerShell stays open.** Every Claude terminal is `powershell -NoExit -Command claude ...`, so if Claude crashes or the user types `/exit`, the terminal stays at a PowerShell prompt, the process does not end, and the card keeps its last state (usually idle). The user can type `exit` in that terminal (then it counts as exited and can be restarted), or close the pair. A `SessionEnd` hook could report it, but `/clear` also ends a session, so it needs a check with a real Claude before it is used.
`- Found on the way: the "⋯" button and the exit overlay of a pair terminal did not react to clicks at all (the click handler only covered the terminal grid, and pair terminals live in the pairs screen); fixed together with T51.

`## The wake never submits the user's draft (T62) — checked once with a real Claude
`- Before: a pair wake pasted its text and pressed Enter 400 ms later, so a half-written message in that agent's input box was merged with the wake text and sent. Now `server/draft.js` knows whether the input has a draft (a shadow of the keystrokes the browser sends, plus the real screen: Claude's input box sits between two `─` rules, its first row starts with `❯`, and the dim (SGR 2) text is only the suggestion) and `Duo.wake()` asks first: no draft = as before; the user is typing (a key in the last 1.5 s, up to 30 s in a row) = wait for the pause; a draft and a pause = **draft swap**; an abandoned draft (no key for 10 minutes) = the wake goes through as it used to, recorded in the feed. A wake that has to wait stays one pending wake per agent (the newest text wins), the agent stays "idle", a quiet "הודעה ממתינה" shows on the card and the pane header, and it is re-checked every 2 s, at once when the user sends or clears the box, and re-validated at the last moment (still needed? pair still running? agent idle?).
`- **Draft swap, verified by hand with a real Claude Code v2.1.301** (dev instance, outside the suite): `Ctrl+S` stashes the current prompt (the box empties, the footer shows `› stashed`), and the next submit restores it by itself about 0.2 s after Enter (footer "Draft restored"); a big paste (`[Pasted text #1 +59 lines]`) survives the stash and comes back as the same placeholder, so nothing is ever re-typed. The server does: lock the browser keystrokes (they queue and are replayed in order afterwards), send Ctrl+S, wait up to 0.7 s for `stashed` on the screen (without that confirmation NOTHING is sent: the wake goes back to waiting; two failures on one agent = wait-only for it), paste the wake, Enter 0.4 s later, wait for the restored draft, release the lock. The whole swap takes about 1 second; a key typed in that second shows up after the restored draft. One constant (`SWAP_DRAFTS` in `server/duo/duo.js`) turns the swap off.
`- The check submitted two harmless one-word messages ("reply with the single word ok") to a real Claude, in this project folder (already trusted, so no trust prompt and no new entry in `~/.claude.json`); each cleared with Ctrl+C and the pane closed.
`- Still depends on Claude Code keeping `Ctrl+S` = stash and the `› stashed` / `❯` / `─` layout. If it changes, the swap simply never confirms and the wake waits for an empty box (the fallback), so a draft can never be sent early; the cost is that a pair waits while the user keeps a draft.

`## Ctrl+A selects the typed text in the Claude input (T63)
`- **What went wrong in the first version (T75, T74).** A user reported that after Ctrl+A the Claude input stopped reacting; it was switched off at once (T75) and then reproduced with the REAL browser key path and a REAL Claude (`node tests/tools/real-claude-keys.js [--on] [--images]`, dev-style server on 7795 with a fresh state file, nothing submitted). Findings: (1) the shipped box detection never matched the real screen, so the feature silently did nothing: Claude puts a NON-BREAKING space (U+00A0) after the `❯` marker (the fixture and the unit tests used a plain space), and its top rule carries a label at the end (`──── duo-worker ─`, the fixture had a plain rule). (2) The real cause of "the typing line is dead": when the focus is NOT in the terminal (for example after a click on a tab or a button) Ctrl+A made the browser select the whole PAGE (102 characters were selected in the measurement) and the next typed keys went to the tab or button, not to Claude. Fix in `shortcuts.js`: Ctrl+A outside a terminal or text field is cancelled and the focus returns to the focused terminal (the first one of the tab when none is focused); the following key reaches Claude (measured). (3) With detection fixed the emulation works for the first time on the real screen, so it was verified end to end with real keys: highlight; typing replaces; Backspace and Delete wipe (also from the middle of a multi-line input); Ctrl+X; Esc and arrow keys clear the highlight and act normally; a mouse click clears it and typing continues; the Hebrew layout (key ש, code KeyA); `[Image #N]` tokens: a pasted image path shows as one token, Ctrl+A on a token alone, and on text + token + text, then Backspace deletes it all (a single plain Backspace right after a token also removes it); the per-pane image list drops the deleted tokens (`dropImages`).
`- **Escape hatches** (a feature that can kill the input must always recover): any key that is not in the documented list clears the highlight AND is delivered to Claude; a highlight older than 15 s, or whose text no longer matches the input (Claude redrew, something was typed elsewhere) is dropped and the key is delivered as a normal key, nothing else is deleted; and `INPUT_SELECT_ENABLED` in `public/js/input-select.js` switches the whole emulation off with one constant. The test fixture now looks like the real screen (NBSP after the marker, labelled rule, image paths become tokens), and `unit/input-select.js` has REAL-screen cases.
`- Claude Code draws its input line itself, so it has no real selection, and for Claude Ctrl+A means "jump to the start of the current line" (readline). In a CLAUDE pane only, Ctrl+A now highlights the text you typed with the normal terminal selection (nothing is drawn over the terminal). While it is highlighted: **Ctrl+C** copies the typed text (no `❯` marker, no indent or box border, Hebrew in logical order, rows that were cut by the width joined with a space, real line breaks kept), **Ctrl+X** copies and deletes, **Backspace / Delete** delete all of it, a **printable key** replaces it, and **any other key** (arrows, Home/End, Esc, Enter, Tab) or a mouse click just removes the highlight and acts normally.
`- It passes Ctrl+A straight through to Claude (never swallowed) when the input is empty (the dim placeholder `Try "..."`), when the box cannot be found with certainty (no rule above and below the cursor, the cursor is outside it, the first row does not start with `❯`/`>`, a "1. Yes" option list), when the agent is waiting for an approval (a dialog is open), or when the process has ended. PowerShell panes and the pair message box are not touched (PSReadLine and the text area already select all).
`- **How the deletion works, checked by hand against the REAL Claude Code v2.1.301** (throw-away session in this folder, nothing submitted, no API call, transcript saving was off so no session file; the findings): Ctrl+A is "start of the current line" (so the cursor can be anywhere in a multi-line input); Ctrl+End does NOT move to the end; Up/Down at the first/last line walk the PROMPT HISTORY (an Up from the first row replaced the input with an old prompt); Ctrl+C **does** clear the input in one key but also arms "Press Ctrl-C again to exit" (a second Ctrl+C quits Claude); Right-arrow at the end of the box can accept the grey prompt suggestion. So the winner is **Delete (ESC [ 3 ~) once for every character after the cursor, then Backspace for every character before it**, counts taken from the buffer and over-estimated on purpose (each row boundary counts as a character, +2 spare): extra Delete at the end and extra Backspace at the start do nothing (also verified on the empty input). It emptied a three-row input from the middle of the second row. Right-arrow to the end then Backspace also worked, but it is not used because of the suggestion. A multi-row input is deleted with exactly the same keys.
`- Empty input detection: the placeholder cells are DIM in the buffer (real captures: `❯ Try "fix typecheck errors"`), typed text is not.
`- The input box layout it relies on (v2.1.301): a horizontal rule, `❯ first row`, continuation rows indented by two columns, a horizontal rule, then the mode line. The older boxed style (╭─╮ │ > text │ ╰─╯) works too; in the box a multi-row highlight also covers the side borders between the rows (single row: exact), the copy never includes them. If a later Claude Code changes this layout the feature falls back to passing Ctrl+A through (nothing to find), it cannot break typing.
`- Wrapped or hard line break? The buffer shows both as separate rows. A row boundary is treated as a soft wrap when the first word of the next row would not have fitted on the previous row; otherwise as a real newline (so a copy never glues two typed lines, and never splits one wrapped line).
